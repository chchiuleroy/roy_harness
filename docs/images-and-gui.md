# 圖片（view_image）與網頁 GUI

> 這份文件是從 [README](../README.md) 拆出來的，**內容原文未改**（只在開頭加這一行與標題）。文中的「見上」「見下」「見某某節」指的是拆開前 README 的位置，現在可能在本資料夾的別份文件裡。

## 圖片（`view_image`）

模型能看圖（作者的 vLLM 上的 Qwen3.6-35B-A3B 在 Hugging Face 上標為 `image-text-to-text`，對該伺服器實測接受 OpenAI 格式的 `image_url`），但 harness 原本的 `read_file` 只讀 UTF-8 文字，所以模型回報「我的工具沒有圖片功能」。`view_image(path)` 補上這一段：

- **兩步**：工具結果只是文字；圖片放在**下一則 user 訊息**（等這批工具結果都附完），以參照 `{"type":"image_ref","path","sha256",…}` 存進 session。**session 檔絕不存圖片位元組**（一張 1 MB 的圖若存 base64，每輪都會被重寫、fsync、重送）。
- **組請求時才讀檔**（`expand_images`）：驗 sha256 後變成 `image_url` data URI，只展開最近 3 張；更早的換成一行文字（`view_image` 可再看）；檔案不見或內容被改了，就換成說明、**不送錯的圖**。
- **檢查**：從檔頭判斷 PNG／JPEG／GIF／WebP 與寬高（不信副檔名、不解碼，不需要 Pillow）；上限 5 MB、3840×2160 像素。
- **預設只對 `vllm` provider 開**（只有它探測過）；`HARNESS_VISION=1` 可強制開其他 provider，此時**託管的第三方 provider（`openai`、`anthropic-compat`）每張圖、每次執行問一次**（截圖可能含機密）。閘看的是 **provider 類型，不是網址**：`vllm`、`llamacpp`、`sglang` 指「你自己的伺服器」，不論它在哪（作者的就在遠端），圖片跟 `read_file` 讀到的文字一樣不問就送過去。
- 圖片內的文字是不可信輸入（跟檔案內容同一類的 prompt injection 風險），工具描述與附帶的提醒都這樣寫。GUI 會顯示「已附上圖片」，重播時不會把它當成你說的話。

**成本（實測，單次，同一台伺服器）**：整個請求的 prompt tokens——256×256 圖 89、640×480 圖 325、1280×720 圖 905、1920×1080 圖 2,065、3840×2160 圖 8,185（含約 20 個字的問句）；伺服器沒有替你縮圖，所以才有像素上限。

**驗證**：`tests/test_harness_vision.py` 26 項（含真實 harness 行程對假伺服器：送出的請求有圖、session 只有參照、重開後再從磁碟讀、jsonl 事件、伺服器拒收圖片時的重試、400 不是圖片造成時不停用圖片、Ctrl-C 後最終存檔仍有圖片）；突變驗證 20 種測試都失敗（送出所有圖片、不驗雜湊、不展開、跳過非本機詢問、摘要逐字稿不處理圖片、圖片放在結果之前、工具永遠提供、信任副檔名、把位元組存進 session；以及下面兩輪審查後新增的 11 種）。

**第三方審查一次**（小o，唯讀、靜態推演）確認 5 項缺陷，全部處理：
1. **（高）換 provider 後舊圖會未經詢問送出**：詢問只發生在 `view_image` 建立參照時，真正送圖的 `expand_images` 沒閘。現在非本機 provider 只送「這一次執行中、人說過可以」的圖（以 sha256 記），其餘換成文字說明；`view_image` 會再問。
2. **（中）平行子 agent 的 call id 相同會串圖**：改以「這批呼叫的物件 id＋批內序號」為鍵，不依賴伺服器給的 id。
3. **（中）崩潰窗口**：工具結果寫入 session 時，「圖片附在下一則訊息」那則訊息還沒寫，崩潰後 session 宣稱已附上、模型永遠收不到。現在每次存檔都把圖片訊息一起寫下（重開時由既有的修復排好順序）。
4. **（低）形狀不合法的舊 `image_ref` 會讓組請求拋 `TypeError`**：一律降級成文字說明。
5. **（低，但後果比寫的大）截斷的假圖通過檢查**：標頭正常、後面缺的檔（下載中斷）會被伺服器拒收，而參照留在 session 裡，之後**每個請求都會失敗**。現在檢查檔尾（PNG 的 IEND、GIF 的結尾符、JPEG 的 EOI、WebP 宣告的長度），並且伺服器對含圖請求回 400 時，**先用不含圖的請求探測一次**。探測成功才確定是圖片造成的，這次執行中不再送圖；探測仍是 400（例如上下文過長）就丟出原本的錯誤、圖片照常保留（這一點是第二輪審查後才改精準的）。代價：檔尾後多了額外資料的圖會被拒絕。

**第二輪複審**（同一位審查者，靜態推演）：除了 Ctrl-C 的追加修復成立外，又確認 5 項，我逐條核對後處理——(a) 400 一律永久停用圖片太粗（改成上面的探測）；(b) 最後一次重試時 400 回退會拋 `unreachable` 蓋掉真正的錯誤（新作法不再用 `continue`，一併消失）；(c) `id(calls)` 重用加極窄窗口可能誤取舊圖（每批開始前先清掉同鍵的舊項）；(d) WebP 沒驗偶數長度與第一個 chunk 是否在宣告範圍內（補上）；(e) 送圖閘不看網址：**屬實，但判為政策而非漏洞**——「自己的伺服器」本來就信任，措辭已改，並用測試固定。Ctrl-C 的追加修復：硬殺行程時圖片訊息有存檔，但乾淨結束（`finish_session` 從記憶體重寫整檔）會把它丟掉，已補，並有測試。

第二輪複審後的這批修復沒有再複審。對真實 vLLM 端到端：模型自己呼叫 `view_image` 讀一張自製的長條圖（標題、最高的長條、三個數字都對；session 檔 1,627 位元組、不含 base64），單次。**沒量**：真實截圖、照片、小字的辨識準確度（只用合成圖）；其他 provider 沒探測。

## 網頁 GUI（`harness_gui.py`）

```bash
python src/harness/harness_gui.py            # 印出帶 token 的網址並開瀏覽器；--port 改埠（預設 8791）、--no-browser 不開
```

多個 session 分頁、左側 session 列表（含續跑）、核准視窗、右側面板（模式、背景任務與停止鈕、`/skills` `/mcp` 等指令按鈕、統計）。**只用標準函式庫**，跟 harness 一樣不需要安裝任何東西。

**架構**：GUI 不 import harness。每個 session 是一個子行程 `harness_vllm.py --jsonl <session 檔>`，工作目錄是你選的專案資料夾；harness 的 stdout 一行一個 JSON 事件（`assistant_delta`、`tool_call`、`tool_result`、`ask`、`usage`、`state`……），stdin 一行一個 JSON 指令（`user`、`answer`）。選一個行程一個 session，是因為 harness 的狀態（模式、MCP、skill、權限）都是模組全域，同一行程塞不下兩個 session；順帶，GUI 掛了不影響 agent、agent 崩了 GUI 還在。不帶 `--jsonl` 的終端機模式輸出與原本逐字相同；jsonl 模式下沒改成結構化事件的 `print()` 會變成 `log` 事件，不會破壞資料流。session 檔放在 `~/.roy_harness_gui/sessions/`（可用 `HARNESS_GUI_HOME` 改），**刻意放在專案資料夾外**，模型的 `write_file` 碰不到。

**核准綁問題 id**：harness 每問一個問題就發一個 `ask`（帶 `rid`），只有帶同一個 `rid` 的 `answer` 才算數；等核准時使用者另外打的訊息不會被當成答案（排隊等這題結束後才處理），過期或錯誤的 id 被丟掉。這是 GUI 版相對終端機版多出來的保護（終端機版下一行輸入就是答案）。

**這個伺服器等於「讓 harness 執行指令的遠端入口」**，所以雖然只綁 `127.0.0.1`，仍做了：每次啟動隨機 token（所有 API 都要帶 `Authorization: Bearer`）；檢查 `Host`（擋 DNS rebinding）與 `Origin`（擋別的網頁）；POST 只收 `application/json`；頁面帶 per-request nonce 的 CSP，頁面本身只用 `textContent`／DOM 節點寫入模型輸出（測試掃原始碼確認沒有 `innerHTML` 等）；請求 body 上限 1 MB。token 放在網址的 `#` 後面，頁面載入後立刻從網址移除。

**停止**是強制結束整棵行程樹，不是「只中斷這一輪」；安全性靠 harness 既有的寫前日誌與重開時補 `INTERRUPTED`（見上）。切換模式送的是 `/mode x`，要等這一輪結束才生效。

**驗證（第一版 GUI）**：`tests/test_harness_gui.py`（離線，真實 harness 子行程對假模型）。突變驗證：拿掉 token／Host／Origin／Content-Type 檢查、讓任何一行都能當核准答案、讓錯誤 id 也能當答案、拿掉啟動鎖，共 7 種，測試都失敗。**第三方審查一次**（小o，唯讀；它的沙盒沒有可寫暫存目錄，所以測試它只看到一項通過，結論是讀程式碼得來的）：確認 4 項缺陷，全部處理——並行續跑會起兩個行程（加啟動鎖）、session 結束後核准卡片還留在畫面（移除）、終端機模式多了不該有的 `flush`（只在原本就有的地方保留）、POST 在驗證前先讀 body（加 30 秒讀取逾時；**殘餘風險**：沒有連線數上限，本機行程仍可開很多慢速連線占住執行緒，但不能藉此通過授權）。**第二次複審**（同一位審查者，靜態推演）：修復 2、3、4 成立；修復 1 引入一個新競態——`stop()` 後立刻 `start()` 時，舊行程的讀取執行緒晚到的 `exited` 會把執行中的新行程顯示成已結束並清掉它的核准問題（medium，已確認）。已改成只有目前的行程能發事件，並先寫了會失敗的測試再修（紅→綠）。**第三次複審**（靜態推演）：該修法的「檢查是不是目前行程」與「加入事件」不是同一步，換行程發生在兩者之間仍可讓過期事件進來（medium，已確認，窗口很窄）；已讓檢查與加入共用換行程時的那把鎖（`_add_if_current`），並加一個把換行程卡在窗口中間的測試（拿掉鎖就失敗）；順手移除沒人讀的 `exit_code`。這次修復沒有再複審；`_pump_err`（stderr）仍不做世代檢查，舊行程晚到的 stderr 行可能混進新行程的記錄，不會影響核准或狀態。

**實測**：用瀏覽器窗格對假模型操作過一輪（建立 session、送訊息、核准、重新整理後重播、停止、續跑）；再對**真實 vLLM**（Qwen3.6-35B-A3B）在瀏覽器裡實測：safe 模式下讀檔＋執行指令、核准卡片、串流回答、ttft 顯示；核准未答時按停止，卡片、分頁圓點、標題都清掉；連點三次續跑只多一個 harness 行程；續跑後模型記得先前內容，並被告知被中斷的那次呼叫是 INTERRUPTED。都是單次手動操作，只在暗色模式、1024 寬看過。

**探索測試找到並修掉的缺口**（2026-11-02，對真實 vLLM 在瀏覽器逐項點過；PR #3 之後又找到的）：

| 缺口 | 現在 |
|---|---|
| token 失效時整頁空白、沒提示；把新網址貼進同一個分頁只改了 `#`，頁面不會重新載入、還是舊 token | 紅色橫幅說明；`hashchange` 時收下新 token 並重新載入 |
| 伺服器掛掉時頁面照樣顯示綠色「執行中」 | 橙色「連線中斷」橫幅，綠點變灰 |
| `/clear` 後模型失憶但畫面沒任何提示 | 分隔線「對話已清除」，舊內容淡化（`cleared` 事件，終端機模式不印） |
| 重新整理後開著的分頁全不見 | 以 `localStorage` 還原分頁與作用中的分頁 |
| 資料夾欄位留空會在伺服器自己的資料夾建立 session | 伺服器回 400、頁面先提示 |
| 關掉有待核准的分頁後，標題提示消失 | 標題也看伺服器端的待核准數 |
| 別的分頁有新回答時沒提示 | 分頁圓點變藍、標題「(新)」（重播的歷史不算新消息） |
| 窄螢幕右側面板整個隱藏、主區只剩 175 px | ≤900 px 時側欄與面板改成抽屜（☰ 列表／⚙ 面板） |
| 回答裡的 markdown 原樣顯示 | `harness_gui_md.js` 轉成資料樹，頁面只用 `createElement`／`textContent`（HTML 與連結一律當文字）；支援標題、清單、**粗體**、`行內程式碼`、程式碼區塊 |
| 指令按鈕每按一次在對話裡多一個「你」的泡泡 | 一行 `› /stats` |
| `compacted` 事件沒顯示 | 「已壓縮對話」一行 |
| 重播歷史時，壓縮摘要、黏在輸入前面的提醒、鬧鐘喚醒通知被當成「你說的話」 | 摘要變成可摺疊一欄、提醒被去掉、通知變成一行 |
| `#newform` 的 `style=` 被 CSP 擋掉，「模式」與「建立」沒排成一列 | 改成 class；測試掃頁面原始碼不得再有 `style=` |

**貼圖／上傳**（共用 `view_image` 的 `image_ref` 管線）：輸入框可以貼上截圖、把圖片拖進對話區、或按 📎 選檔，最多 4 張、每張 5 MB（PNG／JPEG／GIF／WebP）。圖片先 `POST /api/sessions/<id>/upload`（base64 包在 JSON 裡，body 上限 8 MB，其他請求仍是 1 MB）存成 `~/.roy_harness_gui/sessions/<id>.images/<sha256>.<副檔名>`——跟 session 檔一樣在專案資料夾**之外**，模型的 `write_file` 碰不到；`send` 只帶圖片 id（必須是這個 session 自己存過的檔，`names.json` 或路徑穿越都被拒）。harness 端用 `make_image_ref` 做完整檢查（檔頭、檔尾、大小、像素），訊息裡只存參照；人自己附的圖視為已核准（`_APPROVED`），只送給當前 provider 一次。只有圖沒有字也是一則訊息（預設文字請模型看圖說明）。壞圖會在對話裡說「not attached: …」，其餘字與圖照送。`HARNESS_VISION=0` 時圖片丟掉並告知。CSP 多了 `img-src blob:`（縮圖用本機 blob，不載入任何外部圖片）。重播歷史時，打的字和圖都留著（`_user_words` 現在處理含圖片的 list content，壓縮後打字內容不會被當成提醒剝掉）。

**這輪補測找到並修掉的兩個真 bug**（2026-11-02，auto 模式要模型同時開兩個子代理並跑 `python -c`）：

| 缺口 | 現在 |
|---|---|
| **模型執行的 `python -c ...` 在 GUI 下永遠卡住**。GUI 模式下 harness 的 stdin 是指令管道，且有一條執行緒卡在讀它；子行程繼承這條管道，Windows 上它一查 stdin 是什麼類型的 handle 就卡死（`subprocess` 的 `timeout` 也救不了，因為孫行程握著輸出管道）。`echo`、`dir` 這類命令不查 stdin，所以先前的實測都沒踩到。也等於讓子行程能吃掉你的下一則訊息 | `_spawn_args` 一律 `stdin=DEVNULL`；回歸測試 `TestCommandsDoNotShareTheCommandPipe`（拿掉就卡住）。真實 vLLM 重跑：`python -c "print(6*7)"` 回 42 |
| **開到第 6 個 session 分頁，整個 GUI 像當掉**：每個分頁一條永不結束的 `/stream`，瀏覽器對同一個 host 最多 6 條 HTTP/1.1 連線，之後 send／answer／stop 全排不進去（伺服器日誌什麼都沒有，因為請求根本沒送出） | 伺服器對「沒在跑、事件已送完」的 session 結束 stream；頁面把該 view 標成 `parked`，按續跑或輪詢看到它又在跑時才重新接上。瀏覽器實測：6 個還原的分頁，stream 全在約 10 ms 內結束，續跑後事件照常進來 |
